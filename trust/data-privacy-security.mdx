Rundock runs on your machine. Talking to an AI means some content has to leave your machine to be processed. This page explains exactly which content, where it goes, and what happens to it after.

It is written to be forwardable to your IT, legal, or compliance lead during evaluation. End-to-end read time is about five minutes.

## Where your files live

Your workspace is a folder on your machine. The agents, skills, instructions, and any knowledge documents you have added all live in that folder. Rundock builds a search index over it, as a local database file at `.rundock/search-index.db` inside the workspace, and sends it nowhere. Beyond that it does not sync your workspace to a Rundock server or analyse its contents in the background.

Per-user state lives in that same `.rundock/` directory: your conversation list, full message transcripts as plain JSON files, one per conversation, routine run records, the search index above, and the workspace mode. It is local, and it is plain text. You can read a transcript in any editor, search it with `grep`, or delete it with `rm`.

Rundock holds no sign-in of its own. Claude Code and Codex each hold their own sign-in in their own configuration, outside the workspace folder, and Rundock never reads it: it learns that Claude Code is signed in from how its turns go, and that Codex is signed in from whether its `auth.json` file exists. The one kind of credential Rundock does keep is for MCP servers: key values can live in `.rundock/mcp-secrets.json`, a per-user file in the workspace, and Rundock merges them into the server settings only when a Claude Code agent starts, so they stay out of the `.mcp.json` your team shares.

Rundock sends no telemetry, no analytics, no usage events. There is no Rundock account to create. There is no Rundock backend that touches your data.

Rundock itself contacts only GitHub. The desktop app checks GitHub for app updates each time it starts, and downloads them. When you add a package, check one for updates or update one, Rundock fetches it from its GitHub repository. None of your files, agents or conversations go with those requests.

If your team shares a workspace, that sync runs through whatever sync layer you choose: Dropbox, OneDrive, Google Drive, or git. The sync is directly between team members. Rundock does not see it.

Because `.rundock/` sits inside the workspace folder, a shared workspace syncs conversation history, transcripts and run records along with the agents and knowledge files, unless you exclude it. On git, Rundock appends `.rundock/` to the workspace's `.gitignore` when it sets up the workspace. That write is skipped if the file already mentions `.rundock` in any form, and a failure is not surfaced to you, so confirm the entry is present rather than assuming it. On Dropbox and OneDrive you exclude it yourself, and the setup guide records no way to exclude it on Google Drive. If this matters for your evaluation, read [Set up a team workspace](/guides/team-workspace) for the steps and treat the exclusion as required setup. Moving this state out of the workspace folder is planned work.

For the full directory layout, see [Workspace structure](/reference/workspace-structure).

## What gets transmitted

When you send a message to an agent, the following is sent to Anthropic's API via Claude Code:

- Your message and the conversation history for the active conversation
- The agent's instructions (the agent's markdown file)
- Workspace-level instructions if relevant (`CLAUDE.md`)
- Metadata about the team (agent names, descriptions, delegation table)
- Contents of any files the agent reads as part of handling the task

Apart from those GitHub requests, which carry none of your content, Rundock sends nothing beyond the conversation context above: no pre-loading of your wider workspace, no embedding, and nothing from the local search index. Files outside the conversation context stay on disk untouched.

When an agent uses a built-in tool (Read, Write, Grep, Bash), the tool runs locally on your machine. The tool's output may be included in subsequent API calls if the agent reasons about it in its reply.

## Agents on the Codex runtime

If you run agents on the Codex runtime, their conversations are processed by OpenAI instead of Anthropic, under **your own ChatGPT account**: the Codex CLI signs in with your ChatGPT plan, and the data relationship for those agents is directly between you and OpenAI. Rundock's position is unchanged: it starts the CLI locally, sends none of the conversation anywhere itself, and never reads either runtime's credentials (for Codex, sign-in detection checks that its credentials file exists, nothing more). The training and retention terms that apply to Codex conversations are those of your ChatGPT plan; review them in [OpenAI's data controls](https://help.openai.com/en/articles/7730893-data-controls-faq) for your account type.

If an agent connects to a third-party MCP server, that connection sends data to a separate service. Review the MCP server's data handling independently; Rundock's local-first design and Anthropic's protections do not extend to it.

In short: the conversation is the unit of transmission. If a file is not referenced in the conversation, it is not sent.

## Extensions and packages

You can add agents, skills and extensions to a workspace from a GitHub link. Rundock does not review packages, and what you install is your choice, so this section says exactly what protects you and what does not.

**Nothing is written until you accept.** Rundock reads the repository and shows what it contains first. The facts on that screen, such as which files an extension asks to render, whether it can change them, and how many agents, skills and routines come with it, are read from the package itself rather than taken from its author's description. Declining removes everything that was fetched.

**An extension is installed from a tag or an exact commit, never a branch.** A branch names whatever was pushed last, so the code the confirmation screen describes could change after you agree to it. Rundock fetches a tag as a tag, so a branch sharing its name cannot arrive in its place, and the screen names the commit it resolved to. The code you approved is the code that runs. An update is new code, held to the same rule, and is offered only for a newer version tag. It is reviewed under the package's card before anything changes, and the review names any permission the new extension version asks for that the old one did not. Nothing updates on its own.

**Agents and skills from a package are not sandboxed.** Once added, they are ordinary files in your workspace and act with the same access as your own agents, under the same workspace mode, the same approval cards and the same [Keep agents inside this workspace](/reference/workspace-structure#keep-agents-inside-this-workspace) switch. The install screen says so, and names every routine that will run on a schedule. Review them as you would any agent you did not write.

**Starter files never replace yours.** A package can bring files for its agents to work on, such as a portfolio. Each is written only where nothing exists, is named on the install screen first, and is yours afterwards, and an update never replaces it. A package whose starter files include a hidden name or a link is refused whole.

### What the extension sandbox enforces

An extension's view is someone else's code, so it runs confined. Each of the following is enforced by Rundock or by the browser engine rather than asked of the extension, and the confinement is tested in the Chromium engine and in the shipped desktop app against a deliberately misbehaving extension.

- **It cannot reach Rundock's page.** The view runs in a frame whose only sandbox permission is to run scripts, which gives it an opaque origin: no access to Rundock's page, storage, scripts, conversations, or connection to its server.
- **It cannot load pages or make requests.** The view's content security policy refuses every page load, request and external resource. It cannot replace itself with another page: Rundock refuses the navigation, and ends a view that tries. In the desktop app, peer-to-peer connections are switched off for it as well. When you use Rundock in a browser they are not blocked, and the install screen says so.
- **It sees only the file it was opened on, and the files that note names.** It receives that one file's path and text, as a copy, and nothing else about your workspace. It cannot list, search or read any other file. The one addition is a note you mark for it: if the extension asked for it at install, a note can list files under `sources:` in its frontmatter, and the view is handed those, by the names you typed. Nothing is searched for, and no write the extension causes can change that list.
- **It is never given a hidden or linked file.** Files in folders or with names starting with a dot, including your agents' instructions in `.claude/`, Rundock's state in `.rundock/`, `.env` and `.mcp.json`, never open in an extension's view and are never handed to it as a source. Nor is a linked file, a file in a linked folder, or a file with a second name elsewhere, because its visible name could stand for a hidden file or one outside your workspace. Rundock's server decides this from the file itself, and checks again when an extension's change is written.
- **It can say only a fixed set of things.** Rundock checks every message the view sends against a closed list and refuses anything else. The list is published in the [extension host contract](/reference/extension-contract).
- **It cannot act on its own.** Opening another file, opening a web address, or drafting a message to an agent happens only after you click inside the view, and one click allows one request, across every extension view. When Rundock cannot tell that a request came from your click in that view, it asks you in its own bar above the view, with Open and Dismiss, which the extension cannot draw, read or press. A request with no click at all is stopped, and Rundock tells you which extension tried.
- **It cannot reach your agents.** An extension can put a drafted message in a new conversation with an agent its manifest named and the install screen showed you. Nothing is sent until you send it, and the extension never sees the conversation, the reply, or whether you sent it.
- **Web addresses open outside Rundock.** A web link anywhere in Rundock, in an extension or not, opens in your browser, and the app itself never navigates away.
- **Its own settings stay out of your notes.** An extension can keep up to 64 KB of its own preferences for each note it opens, such as column widths, in Rundock's own folder, never in your notes. They are never handed to any other view, and uninstalling the package removes them.
- **It changes only what it was allowed to.** An extension can save only the file it was opened on, and the files that note names, only when its manifest asked for that, and the install screen tells you when it did. It cannot name any other file to write.
- **Its components are Rundock's, with no extra reach.** Rundock puts its own component library into every extension view. It runs inside the view with the view's limits, sends nothing and fetches nothing, so it widens nothing above.
- **It is removed cleanly.** Switching an extension off, pausing every extension, or updating or uninstalling its package ends its view, and uninstalling deletes its files under `.rundock/extensions/`. Agents and skills you have edited, and every starter file, stay, because they are yours.
- **You can turn every extension off at once.** **Pause all extensions**, under Settings, Extensions, turns them all off without changing any extension's own setting, and **Resume extensions** brings each one back to its own setting. While an extension is off, paused or by its own switch, Rundock refuses to serve its code to any window and tells every open window, which ends a view that is showing.

For what building an extension within these limits looks like, see [What an extension cannot do](/extending/limits).

## Training

Anthropic's Commercial Terms state directly that "Anthropic may not train models on Customer Content from Services". Inputs and outputs sent to the API are not used to train Anthropic's models unless you opt in.

Anthropic publishes this in two places:

- [Commercial Terms](https://www.anthropic.com/legal/commercial-terms) (Section B, "Customer Content")
- [Is my data used for model training?](https://privacy.claude.com/en/articles/7996868-is-my-data-used-for-model-training)

How Claude Code has been authenticated matters here:

- **Claude Code via an Anthropic API key (from a Commercial organisation).** Anthropic's Commercial Terms apply. API content is not used for training by default. Data Processing Addendum (DPA), Zero Data Retention (ZDR), and HIPAA-ready API access are all available on this path.
- **Claude Code via a Claude Pro or Max subscription.** Anthropic's consumer terms apply. Pro and Max are not eligible for ZDR, a DPA, or HIPAA-ready API access. The relationship is a consumer one, not a commercial one.

For business and regulated use, use a Commercial-organisation API key. The Commercial Terms are the right contract for confidential client work and they unlock the protections that consumer plans do not offer.

## Retention and Zero Data Retention

For commercial API customers without a ZDR arrangement, Anthropic's [commercial data retention policy](https://privacy.claude.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data) states that "we automatically delete inputs and outputs on our backend within 30 days of receipt or generation". Stateful features such as the Batch API and the Files API carry their own retention windows documented per feature, but standard Claude Code inference sits under that 30-day default.

For organisations that need stricter handling, Anthropic offers **Zero Data Retention (ZDR)** for Claude Code. With ZDR enabled, prompts and model responses generated during Claude Code sessions are not stored by Anthropic after the response is returned, except where needed to comply with law or combat misuse.

ZDR for Claude Code is available through two paths:

- **Commercial-organisation API keys.** Pay-as-you-go API keys from a Commercial organisation can have ZDR enabled on request.
- **Claude Enterprise.** Claude Code through Claude Enterprise can have ZDR enabled for the organisation.

ZDR is enabled per organisation by Anthropic's account team. Even with ZDR in place, Anthropic may retain inputs and outputs for up to two years where required by law or to address Usage Policy violations. Third-party tools an agent connects to from your workspace, including MCP servers, are not covered by ZDR; review them independently.

For the full ZDR scope, see Anthropic's [API and data retention](https://platform.claude.com/docs/en/manage-claude/api-and-data-retention) and [Claude Code ZDR](https://code.claude.com/docs/en/zero-data-retention) documentation.

Worth being clear on division of responsibility: Rundock keeps everything local except for what gets sent to the API. ZDR controls what Anthropic does with the data once it arrives. The two are different protections, applied at different layers. Rundock cannot enable ZDR on your behalf; that is a contract between you and Anthropic.

## Who owns the data relationship

You bring your own Anthropic credentials to Claude Code. This is the BYOK ("bring your own key") model.

In practice that means:

- You or your firm hold the contract with Anthropic
- API charges go to your account
- The terms governing your data (commercial terms, DPA, ZDR addendum if you have one) are between you and Anthropic
- Rundock has no account, no key, no proxy, and no log of your API traffic

If your IT or compliance lead asks "who is the data processor and who is the data controller", the answer is straightforward: you are the controller, Anthropic is the processor for the LLM work, and Rundock is locally installed software that does not sit in the middle.

This is intentional. Rundock is the orchestration layer on your machine. The data relationship that matters for compliance sits between your business and Anthropic; routing it through Rundock would add a third party with no compliance benefit.

## In summary

If you are forwarding this page to someone who needs the headlines:

- Your files stay on your machine. Rundock has no backend, no telemetry, no account. Rundock itself contacts only GitHub, for app updates and packages, and sends none of your content there
- Only the active conversation goes to Anthropic for processing; nothing else
- With a Commercial-organisation API key, content is not used to train models by default, and Anthropic deletes inputs and outputs within 30 days
- Zero Data Retention is available on request via the Commercial API or Claude Enterprise; it removes the 30-day window for Claude Code inference
- Third-party MCP servers an agent connects to are outside Rundock's local scope and outside Anthropic's ZDR; review them independently
- Extensions are installed from a tag or an exact commit, run sandboxed so they cannot load pages or make requests (peer-to-peer connections are blocked only in the desktop app), see only the file they were opened on and any files that note names, and act only on your click; agents and skills installed from a package are not sandboxed and act like your own
- The contractual relationship for the data is between your business and Anthropic, not Rundock

Forward this page to whoever needs to sign off, then talk to your Anthropic representative about contract terms.
