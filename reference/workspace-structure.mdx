A Rundock workspace is a folder. This page is the canonical reference for what is inside that folder, where each thing lives, and what syncs across a team versus what stays on the individual machine.

For the concept, see [Workspaces](/concepts/workspaces). For the team setup walkthrough, see [Set up a team workspace](/guides/team-workspace).

## Top-level layout

```
your-workspace/                   # the workspace folder itself
├── .claude/                      # agent and skill files (hidden by default)
│   ├── agents/                   # one markdown file per agent
│   ├── skills/                   # one folder per skill
│   └── settings.local.json       # per-user MCP and permission overrides
├── .rundock/                     # per-user state (hidden, inside the workspace)
│   ├── conversations.json        # the conversation list
│   ├── lists.json                # how conversations are grouped
│   ├── state.json                # workspace mode, sandbox switch, working folders, setup state
│   ├── pins.json                 # the files you have pinned
│   ├── permissions.json          # your "Always allow" answers
│   ├── mcp-secrets.json          # your MCP credential values
│   ├── mcp-runtime.json          # .mcp.json merged with those values, for Claude Code agents
│   ├── reviews/                  # comments on files you have reviewed
│   ├── transcripts/              # one JSON file per conversation
│   ├── runs/                     # one record per routine run
│   ├── routine-state.json        # last-run state, so a restart does not double fire
│   ├── routine-slots.json        # which scheduled slots have been served
│   ├── child-pids.json           # process ids for running agents
│   ├── scratch/                  # working files written while an agent runs
│   ├── startup.log               # server startup log
│   ├── search-index.db           # the search index
│   ├── extensions.json           # the extensions you have installed
│   ├── extensions/               # each installed extension's files
│   ├── extension-state/          # each extension's own preferences, per note
│   ├── receipts/                 # what each package install and update did
│   └── package-updates/          # author versions and backups saved by updates
├── .mcp.json                     # workspace-level MCP server config (optional)
├── CLAUDE.md                     # workspace-wide instructions
└── [knowledge files]             # anything else you add
```

The workspace folder is the unit of sharing, and everything in it syncs when the folder syncs. That includes `.rundock/`. The `.claude/` directory, `CLAUDE.md` and your knowledge files are meant to be shared. `.rundock/` is per-user state that lives in the same folder for now, so on a shared workspace you exclude it deliberately: see [What syncs and what does not](#what-syncs-and-what-does-not) below.

## What each path is for

### `.claude/agents/`

One markdown file per agent. The filename without the `.md` extension is the agent's slug.

```
.claude/agents/
├── chief-of-staff.md             # the orchestrator
├── content-lead.md               # specialists
├── lead-developer.md
└── ...
```

Each file has YAML frontmatter at the top (declaring identity, position, icon, colour) and a markdown body underneath (the agent's system prompt). For the full reference, see [Agent file format](/reference/agent-file-format).

### `.claude/skills/`

One folder per skill. The folder name is the skill's slug. Inside each folder, a single `SKILL.md` holds the skill definition.

```
.claude/skills/
├── linkedin-hook-generator/
│   └── SKILL.md
├── voice-editor/
│   ├── SKILL.md
│   └── references/
│       └── tone-examples.md
└── ...
```

The folder shape exists so a skill can keep references, templates, sub-files, and assets next to its definition. For the full reference, see [Skill file format](/reference/skill-file-format).

### `.claude/settings.local.json`

Per-user MCP server permissions and tool overrides for the workspace. Although it sits inside `.claude/`, this file should not sync across team members: it is per-user state. Add it to your sync tool's exclusion list (or to `.gitignore` if you sync via git).

### `.mcp.json`

Workspace-level MCP server configuration. Lists the MCP servers the workspace uses and the connection details. This file syncs across the team on every sync option, git included, so any key written into this file syncs with it. Put credential values in `.rundock/mcp-secrets.json` instead, keyed by server name: Rundock merges them in only when a Claude Code agent starts. A key already in `.mcp.json` keeps working until you move it. Read the file before you share the workspace folder.

This file is optional. If your workspace uses no MCP servers, omit it.

### `CLAUDE.md`

Workspace-wide instructions. Rules and context that apply to every agent in the team. House style, file path conventions, naming rules, anything you want every agent to follow.

CLAUDE.md is loaded as part of every agent's context at spawn time. Keep it focused: long, dense rules in CLAUDE.md slow every conversation down. House style and shared file path conventions belong here. Domain-specific procedures belong in skills.

### Knowledge files

Anything else you add to the workspace folder. Brand documents, ICP definitions, voice profiles, pricing pages, reference material your agents need to read. There is no required structure: organise these however suits your work.

A common shape:

```
your-workspace/
├── .claude/
├── CLAUDE.md
├── 00_Inbox/
├── 01_Projects/
├── 02_Areas/
│   ├── Marketing/
│   ├── Sales/
│   └── Engineering/
└── 03_Reference/
```

Agents read these files when their instructions tell them to. Rundock does not auto-load them at spawn time: you control which files come into context, by writing it into the agent's body or skill instructions.

### `.rundock/`

Per-user state, in a hidden directory at the root of the workspace folder. Rundock creates it when it sets up a workspace, and appends `.rundock/` to the workspace's `.gitignore` at the same time. Holds:

- **`conversations.json`**: the conversation list. **`lists.json`**: how those conversations are grouped.
- **`transcripts/`**: full message transcripts, one JSON file per conversation, named by its id. A conversation that delegates keeps every agent's part in the same file.
- **`runs/`**: routine run records, one file per run. **`routine-state.json`** and **`routine-slots.json`**: the scheduling state behind catch-up.
- **`state.json`**: the workspace mode (Notes or Code), whether agents are kept inside the workspace (`sandboxSwitch`), the [folders agents can also change](#folders-agents-can-also-change) (`workingFolders`), setup state, and a record of where the workspace was last seen, which Rundock compares against the current path to notice that the folder has moved. The list of workspaces you have opened is kept separately: in your home directory in the desktop app, and beside the server's own code when Rundock is run from source.
- **`search-index.db`**: the search index. **`scratch/`**, **`child-pids.json`** and **`startup.log`**: working files for running agents.
- **`pins.json`**: the files you have pinned. **`permissions.json`**: the "Always allow" answers you have given on permission cards. **`reviews/`**: the comments you leave when reviewing a file.
- **`mcp-secrets.json`**: your MCP credential values, keyed by server name, holding only each server's `env` and `headers`. **`mcp-runtime.json`**: `.mcp.json` merged with those values, written when a Claude Code agent starts. Both hold keys, so keep them out of any sync.
- **`extensions.json`** and **`extensions/`**: the extensions you have installed, each with the source and version it was pinned to, and its files. Uninstalling its package removes both. **`extension-state/`**: each extension's own preferences for the notes it opens, such as column widths, one folder per extension and one file per note, kept on this machine and never in your notes. Uninstalling the package removes that extension's folder. **`receipts/`**: one receipt per package install or update, listing what arrived, what you decided for each item, the exact commit fetched, and a fingerprint of each file as it was written; a package's receipts are removed with it when you uninstall it. **`package-updates/`**: the author's versions of anything an update kept as yours, and backups of what it replaced, one folder per package. Kept on this machine only until you clear them from the Packages page. See [Install a package](/extending/install-a-package).

Your runtime sign-in lives elsewhere: Claude Code and Codex each hold their own in their own configuration, outside the workspace folder, and Rundock reads none of it. Rundock does not hold your Claude or ChatGPT sign-in. The only keys it keeps are the MCP credential values in `mcp-secrets.json`.

<Warning>
`.rundock/` is inside the workspace folder, so it syncs whenever the workspace folder syncs. Without an exclusion, every message exchanged with your agents is readable by anyone with access to the folder.

On git, Rundock writes the exclusion for you at setup, with two limits worth knowing. It skips the write when the `.gitignore` already mentions `.rundock` in any form, including a different filename that merely starts the same way, and a failed write is not surfaced anywhere you would see it. **Confirm your `.gitignore` contains `.rundock/` rather than assuming it.**

On Dropbox and OneDrive you exclude it yourself. [Set up a team workspace](/guides/team-workspace) has the steps for each tool, and records no way to exclude it on Google Drive.
</Warning>

<Note>
Moving conversation history out of the workspace folder, so that excluding it is no longer necessary, is planned work. `.mcp.json` stays where it is.
</Note>

## What syncs and what does not

The split as a table.

| What | Where | Syncs? | Why |
|---|---|---|---|
| `.claude/agents/` | Workspace folder | **Yes** | The team is shared. Every member should have the same agents. |
| `.claude/skills/` | Workspace folder | **Yes** | Skills are reusable workflows. Every member should have access. |
| `CLAUDE.md` | Workspace folder | **Yes** | House rules apply to everyone. |
| `.mcp.json` | Workspace folder | **Yes** | Shared with the whole team on every sync option. Any API key written into it syncs too, so keep keys in `.rundock/mcp-secrets.json`. |
| Knowledge files | Workspace folder | **Yes** | Brand documents, voice profiles, reference material are team assets. |
| `.claude/settings.local.json` | Workspace folder | **Yes, unless excluded** | Per-user permission and MCP overrides, meant to stay on one machine. Rundock does not write this exclusion, so add it to your sync tool's exclusion list, or to `.gitignore` if you sync via git. |
| `.rundock/conversations.json`, `.rundock/transcripts/` | Workspace folder | **Yes, unless excluded** | Your conversation list and every message transcript. Meant to be per-user. |
| `.rundock/runs/` | Workspace folder | **Yes, unless excluded** | One record per routine run, so this grows with every scheduled run. |
| `.rundock/state.json`, `.rundock/search-index.db` | Workspace folder | **Yes, unless excluded** | Workspace mode, the sandbox switch, working folders, setup state, last-seen path, and the search index. |
| `.rundock/mcp-secrets.json`, `.rundock/mcp-runtime.json` | Workspace folder | **Yes, unless excluded** | Your MCP credential values. Keep them on your machine. |
| `.rundock/pins.json`, `.rundock/permissions.json`, `.rundock/reviews/` | Workspace folder | **Yes, unless excluded** | Your pins, your "Always allow" answers, and your review comments. |

Everything in the `.rundock/` rows is covered by the `.gitignore` entry Rundock writes at setup, subject to the two limits in the warning above, and has to be excluded by hand on Dropbox and OneDrive. The guide records no way to exclude it on Google Drive.

The principle: **agents and shared knowledge belong to the team, and conversations belong to the individual.** Today both sit in the same folder, so the second half of that holds only once you have excluded `.rundock/` from your sync tool.

## Hidden folders

The `.claude/` directory is hidden by default in Finder (Mac) and File Explorer (Windows). This is standard behaviour for any folder name starting with a dot.

Cloud sync services handle hidden folders correctly. They sync the same way as visible folders. If you want to inspect the contents directly:

- **Mac:** in Finder, press `Cmd + Shift + .` to toggle hidden file visibility.
- **Windows:** in File Explorer, View > Show > Hidden items.

## Workspace mode

Workspace mode is a workspace-level setting that changes agent behaviour at the platform level. Set per workspace, not per agent.

| Mode | What it changes |
|---|---|
| **Notes** (default) | Restricts file writes for executable file types (`.js`, `.py`, `.sh`, etc) so agents cannot accidentally write or modify code in a workspace of notes and documents. Commands that change something ask first. |
| **Code** | Removes the executable-file write restriction. Auto-approves common build and dev tools so agents can iterate on code without permission card interruptions. Used for software project workspaces. |

Mode is set in **Settings**, under **Permissions**, where it is the question **What are you working on?**, or by editing `.rundock/state.json` directly:

```json
{
  "workspaceMode": "code"
}
```

The stored values are `notes` and `code`. A workspace an earlier release stored as `knowledge` is read as Notes, and stays as it is until you change the mode.

When a workspace is first opened, Rundock auto-detects the likely mode by looking for `package.json`, `pyproject.toml`, `Cargo.toml`, and similar markers.

The mode affects every agent in the workspace, not just one. There is no per-agent override.

## Keep agents inside this workspace

Whether agents can change files outside the workspace folder is its own switch, **Keep agents inside this workspace**, in **Settings**, under **Permissions**, below the mode. It is independent of the mode: switching between Notes and Code never moves it. It uses macOS's built-in sandbox, and it applies to Claude Code agents.

- **On:** agents can change files in this workspace and the temporary folders they need. Changes elsewhere are blocked.
- **Off:** agents can change or delete files outside this workspace wherever your account allows. Your approval settings still apply.

A workspace Rundock opens for the first time starts with the switch on, in both modes. Turning it off asks first, "Agents will be able to change or delete files outside this workspace wherever your account allows. Your approval settings still apply.", with **Keep it on** and **Turn it off**.

A workspace set up by an earlier release keeps the state it had, and shows a one-time notice: "Keeping agents inside this workspace is now its own switch. Yours is still on. Switching between Notes and Code won't change it." (or "still off").

The row always states what is in force, in one word beside it:

| State | When |
|---|---|
| **On** or **Off** | macOS. The switch is shown where Rundock controls the setting. |
| **Unavailable** | Windows and Linux, or a Mac where the sandbox cannot run. Your approval settings still apply. |
| **Status unknown** | Where Codex is the workspace's default runtime. Codex runs its own sandbox, from its own config file, and Rundock cannot confirm whether it is active. See [Runtimes](/concepts/runtimes#permissions-and-sandboxing). |

Where something other than Rundock decides, the row is read-only, with a lock and a line naming who:

- **Rules you wrote yourself.** If `.claude/settings.local.json` holds a sandbox block that Rundock did not write, the row shows its state and says it was set up outside Rundock. **Bring your custom rules into Rundock** opens a review first: it lists each folder you added by hand, which becomes one of the folders below, and names any rule Rundock cannot represent, which is dropped. Nothing changes until you choose **Bring in my rules**, and if the file changed after you reviewed it, nothing is brought in and you are asked to review it again.
- **Another settings file turns it on.** Claude Code turns the sandbox on when any of its settings files does. If your organisation's managed Claude Code settings, the project's `.claude/settings.json` or your own `~/.claude/settings.json` turns it on, the row reads **On** and names which, because Rundock's switch cannot turn it off while that file turns it on.

The switch is stored in `.rundock/state.json` as `sandboxSwitch`, and applied through the sandbox block Rundock writes into `.claude/settings.local.json`.

### Folders agents can also change

Under the switch is a list of folders agents can change as well as the workspace, such as a projects folder beside it. Naming a parent, such as `~/Projects`, covers everything inside it, including folders created later. The list is in force whether the switch is on or off, and the line above it says what it does in each case:

- **Switch on:** agents can change files in these folders too. Anywhere else, changes are blocked unless you approve them.
- **Switch off, Code:** agents can change files in these folders without asking. Anywhere else, Rundock asks before a file edit, and before a command it can see reaching outside.
- **Switch off, Notes:** agents can edit files in these folders without asking. Anywhere else, changes need your approval.

A permission card for a file outside the workspace offers **Always allow this folder**, which adds that folder to the same list, for this workspace only. A folder that has gone, such as a drive that is not mounted, stays named and starts covering again if it comes back. Codex agents are unaffected by the list, and `~/.claude` is never included, so your credentials always ask. Removing a folder applies to new conversations; one already running keeps the folders it started with.

The list is stored in `.rundock/state.json` as `workingFolders`.
