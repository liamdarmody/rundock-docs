A Rundock workspace is a folder on your computer. Everything Rundock uses for one team lives inside that folder: the agent files, the skill files, the workspace-level instructions, and any shared knowledge documents you add. When you open Rundock and select a workspace, it loads everything in the folder.

Workspaces are the unit of separation in Rundock. One workspace is one team. If you want different teams for different parts of your business (a client team and a personal team, for example), you create separate workspaces and switch between them.

## What is in a workspace

Inside a workspace folder, the structure looks like this:

```
your-workspace/
  .claude/
    agents/         # one markdown file per agent
    skills/         # one folder per skill, each with a SKILL.md
  CLAUDE.md         # workspace-wide instructions
  [knowledge files] # anything else you add
```

What each part is for:

- **`.claude/agents/`**: the agent definition files. One markdown file per agent. The filename is the agent's slug.
- **`.claude/skills/`**: the skill definition files. One folder per skill, with a `SKILL.md` inside. Skills are reusable instructions an agent can run.
- **`CLAUDE.md`**: the workspace-wide instructions. Rules and context that apply to every agent in the team. House style, file path conventions, any guidance you want every agent to follow.
- **Knowledge files**: anything else you put in the folder. Brand documents, ICP definitions, pricing pages, voice profiles, reference material your agents need to read.

The `.claude/` folder is hidden by default in Finder and File Explorer. Cloud sync services handle hidden folders correctly: they sync exactly the same way as visible folders. If you want to inspect the contents directly, enable "Show hidden files" in your file browser.

Concept first, syntax second. The full directory layout reference is being added under the Reference section. The pieces above are what you need to understand the model.

## What syncs, what stays local

A workspace is split into two parts: the shared team content, and the per-user state. Today both live inside the workspace folder.

**The workspace folder syncs.** Everything inside the folder is meant to be shared across the team. Agents, skills, workspace instructions, and knowledge documents. When the team admin adds a new agent, every team member gets it. When someone updates a skill, the change propagates. The full setup for sharing a workspace across a team is on the [team workspace setup guide](/guides/team-workspace).

**Per-user state lives in `.rundock/`, a hidden directory at the root of the workspace folder.** It holds:

- Your conversation list, and full message transcripts, one file per agent session.
- Routine run records, one file per run, and the scheduling state behind them.
- The search index, the workspace mode, and scratch files written while an agent works.

**Because `.rundock/` sits inside the workspace folder, it syncs when the workspace folder syncs.**

On git, Rundock appends `.rundock/` to the workspace's `.gitignore` when it sets up the workspace, creating that file if there is none. Two things are worth knowing before you rely on it. It skips the write if the `.gitignore` already mentions `.rundock` anywhere, so a file that names something like `.rundock-recent-workspaces.json` never gets the entry added. And if the write fails, it fails quietly. **Open your `.gitignore` and confirm it contains `.rundock/` before you push.**

On Dropbox, OneDrive, and Google Drive nothing excludes the directory by default, so you exclude it yourself. The [team workspace setup guide](/guides/team-workspace) gives the steps for each tool, and records no way to exclude it on Google Drive.

`.mcp.json` is in the same position. It holds your MCP server configuration, it lives in the workspace folder, and it syncs on every option including git. MCP servers commonly take an API key directly in that file, so read it before you share the folder.

Two things do stay on your machine wherever your workspace lives. Your Claude or ChatGPT sign-in is held by the runtime's own command-line tool, in its own configuration outside the workspace folder, and Rundock never reads it. Your recent-workspace list is a small file in your home directory recording which folders you have opened.

The split as a quick table:

| Shared with the team | Per-user, in `.rundock/` |
|---|---|
| `.claude/agents/` | Conversation list and transcripts |
| `.claude/skills/` | Routine run records |
| `CLAUDE.md` | Search index and workspace mode |
| Knowledge documents | Scratch files |

<Note>
Moving conversation history and MCP configuration out of the workspace folder, so that excluding them is no longer necessary, is planned work. Until it lands, treat the exclusion as required setup on any cloud sync tool.
</Note>

## Single-workspace model today

Rundock's current model is one workspace per team. Every member of the team sees the same agents and skills, with no per-team or per-role permission tiering inside the workspace.

This is the right shape for solopreneurs and small teams. As your team grows, you may want finer-grained organisation: separate company-level agents, team-specific agents, and personal agents, with controlled visibility between layers.

Finer-grained workspace organisation is on the roadmap. Until it ships, the supported pattern is one synced folder per team. The [team workspace setup guide](/guides/team-workspace) covers it in full.

## Mid-conversation updates

A specific behaviour worth knowing about: when an agent file is updated while you are mid-conversation, the change takes effect at the start of your next conversation, not in the active one. Active conversations continue with the version that was loaded when they began. If you are tweaking an agent and want to see the effect, finish the current conversation and start a fresh one.
