A routine is a scheduled prompt sent to a specific agent on a cadence. The same prompt the user would type, fired automatically at a time the user defines.

Routines power the kind of automation that needs to happen unattended: a morning briefing on the orchestrator, an end-of-day sync that processes the day's meeting notes, a weekly research digest that runs before the user is awake. They are the scheduled equivalent of clicking "send" on a prompt every day.

## Add a routine

The normal way in is the Add routine form, reached from an agent's page or from the routines panel. It is two short steps:

1. **Pick a skill.** Every routine schedules one of the agent's existing skills. There is no freeform prompt field: the instruction is derived from the skill you pick, so what fires is always something the agent already knows how to do.
2. **Say when.** Choose a frequency (daily, or a specific weekday) and a time, in one plain sentence: "Run Weekly research digest every Friday at 4:00am, on this computer." Confirm, and the routine is live.

Under the hood, both routes write the same thing: a `routines:` entry in the agent's frontmatter. A routine made in the form and one written by hand are the same routine; the form is just the fast, correct path through the format documented in [Routine format](/reference/routine-format).

An existing routine's schedule can be changed the same way, without deleting and recreating it: open the routine and pick a new time.

For a full walkthrough with screenshots, see [Set up a routine](/guides/set-up-a-routine).

## What a routine looks like once it's running

The routines panel shows every routine across every agent in the workspace, one flat list. Once a routine has run at least once, its row shows what happened last time, in one of four tones:

- **Ran** — the routine fired on schedule and finished. Shown in the success colour.
- **Caught up** — Rundock was closed at the scheduled time and the routine fired once you opened it again. Also a success, just a quieter one: the row names both the time it actually ran and the time it was due, so the delay reads as legible rather than alarming.
- **Missed** — a scheduled slot went by with Rundock closed, and it fell outside the same-day catch-up window. This is history, not an error: the row names the cause (Rundock was closed) rather than treating it as a failure.
- **Failed** — the run actually failed. This is the only one of the four that gets an alarming colour, on purpose: a routine that ran late or was missed while your laptop was shut is the ordinary case for most setups, and dressing that up as a warning teaches you to ignore the one signal that matters.

While a routine is actively running, its row shows "Still going" instead, with a way to open it and watch. This is the first release where you can do that: before, the row went blank for as long as a run was in progress.

## See what a run did

Every run leaves a record: the files it changed, when it started, how long it took, and how it ended. Reach it from a "View run" link on a routine still going, or "View last run" once it has finished.

The run screen shows one of five outcomes, each in its own words so they cannot be mistaken for one another:

- **Finished** — the run got to the end and did what it was asked to.
- **Stopped early** — the run started and did not get through what it was asked to (a real failure).
- **Stopped** — you asked the run to stop, and it ended. Deliberately not read as a failure: this ending was witnessed, it just was not the one the routine was working towards.
- **No ending recorded** — Rundock closed while the run was under way, so nothing recorded how it turned out. Also not read as a failure: it may have finished a moment before Rundock closed, and nothing here claims otherwise.
- **Still going** — self-explanatory, and the one state that offers the Stop control described below.

Below the outcome, the run's file list: what it changed, or an honest statement of why that can't be known (a shell command that wrote a file leaves no path to report; work handed to a subagent is tracked by that subagent, not this run).

## Stop a run in progress

A run's own screen carries a Stop control whenever it is still going, including in the brief window before its process has actually started. Pressing it shows "Stopping…" immediately; the run ends in its own time; its record then reads **Stopped**, with a real duration, since the ending was witnessed.

Stopping a run does not cancel the routine. It runs again at its next scheduled slot, same as any other routine, just not again in the period you stopped it.

## What routines are good for

Three patterns that work well in practice.

**Morning briefing on the orchestrator.** Fires at 5am, runs whatever the orchestrator's body defines as "session start". Writes the briefing to the day's note so the user sees it when they open the workspace.

**End-of-day sync on the executive assistant.** Fires at 9pm, pulls the day's meetings from a meeting tool, writes meeting notes, creates Todoist action items, updates the people graph.

**Weekly research digest on a research-focused agent.** Fires once a week before the user is awake. Runs a long pipeline (LinkedIn analysis, competitor scan, trending research) and writes a digest to a known folder.

The shape that ties these together: the routine is doing context-heavy work outside working hours, so it does not consume tokens during interactive sessions. By the time the day starts, the work is on the user's desk.

## How the scheduler behaves

The scheduler ticks every 60 seconds. On each tick, Rundock checks every routine on every agent and fires any whose schedule has come due.

Each routine has a `lastRun` guard so daily routines do not re-fire the same calendar day, and weekly routines do not re-fire on the same weekday they last ran on. The guard is held in memory.

When a routine fires, Rundock spawns a headless Claude Code subprocess with the routine's prompt as the input message. The subprocess runs with skipped permissions, because there is no user available to approve tool calls in real time.

## Limits worth knowing

Be honest before getting attached to routines.

<Warning>
**Routines fire only while Rundock is running, but a missed slot is caught up the same day.** Close the laptop at night and open it at 09:00, and a 05:00 routine runs at 09:00. Run state persists across restarts, so nothing fires twice. The limits are that routines run late rather than on time, and that a whole day with Rundock closed is a day the routine does not run at all.
</Warning>

<Warning>
**Routine output itself is not captured to a visible conversation.** When a routine fires, the spawned Claude Code subprocess produces output on stdout and stderr, and Rundock discards both. It records the routine's `lastRun` timestamp, status, and duration, and a separate record of the files the run changed (see above), but it does not surface the model's response or its running commentary in a Rundock conversation.

Practical implication: any routine that needs to leave a trace must write that trace itself, through tools. A morning briefing writes to the day's note. A digest writes a markdown file to a known folder. An end-of-day sync writes Todoist tasks via MCP. A routine that asks the model to think out loud will produce output nobody ever reads.
</Warning>

<Note>
**No notification when a routine completes.** You notice a routine ran by either seeing the row update in the routines panel, or seeing the file the agent wrote, or seeing the tasks the agent created.
</Note>

<Note>
**Schedule format is exact and quietly fails on bad input.** Cron expressions are not supported. Times must be two-digit zero-padded. Weekdays must be lowercase, full word. A routine with an unrecognised schedule registers without errors and never fires. If a routine appears to do nothing, the schedule string is the first thing to check. See [Routine format](/reference/routine-format) for the full pattern reference.
</Note>

## Always-on routines

If you want routines to fire while you are away from your computer, two practical paths.

**Run Rundock on a small VPS.** Keep Rundock running on a cloud server (Hetzner, DigitalOcean, Hostinger, etc) and reach it from any device through a browser. The scheduler ticks 24/7, routines fire on cadence regardless of whether your laptop is open. Costs around £5 to £10 per month plus a couple of hours of initial setup. The trade-off is real but small.

**Use Anthropic's managed Claude Code Routines.** Anthropic shipped a managed scheduling layer that fires Claude Code sessions on their cloud infrastructure. Available on Pro, Max, Team, and Enterprise plans with Claude Code on the web enabled. The minimum recurring interval is one hour. See the [official docs](https://code.claude.com/docs/en/routines) for the full feature set.

Anthropic's Routines and Rundock's routines are complementary, not interchangeable. Rundock routines run inside your local agent team with full read and write access to the workspace. Anthropic's Routines run inside a Claude Code cloud environment with access to whatever you wire into it (primarily GitHub repositories and remote connectors). They do not see your local vault or your Rundock agent definitions.

The split that tends to work in practice: keep workspace-bound routines (morning briefings, end-of-day syncs, anything that depends on local files) on Rundock and host Rundock on a VPS if you need 24/7 firing. Move repo-bound work (PR triage, scheduled code review, release notes) to Anthropic's Routines.
